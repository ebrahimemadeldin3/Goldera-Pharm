# Manager overview data contract

The /manager route uses the authenticated GET /api/dashboard/managers/overview endpoint. Data is aggregated in PostgreSQL/Prisma rather than collected by downloading every paginated record. The previous manager components remain for compatibility; the live route uses ManagerOverviewDashboard.

## Important data limits

- The sales ledger does not store representative ownership. Representative filters never invent sales credit. This is explicitly disclosed in the interface.
- Geographic sales attribution uses exact customer names only where the pharmacy name is unique. Unmatched or ambiguous sales remain in company totals and are excluded from geographic filtering, with counts disclosed.
- Directory geography uses configured backend territory names. Districts classify configured regions using the existing Manager district terminology; unrecognized regions appear as Other Regions. No static list of fictitious/unassigned territories is rendered.
- Employee, doctor and pharmacy assignments are current records; historical territory assignments are not stored. Date labels do not imply historical employee status or directory membership.
- Dates use Asia/Riyadh, matching the product's Saudi business calendar. Weeks begin Sunday. Ranges above 90 days use monthly trend buckets; custom ranges are limited to five years.

## Failure and recovery

Each source uses a repeatable-read transaction to keep its totals and charts consistent. Seven sources are loaded independently: visits, sales, directory, team, coaching, appraisals and workflow. A section failure returns data: null and a source/code/request reference, not zero records. Successful sources remain visible. Retry and Refresh issue a new authenticated request; stale responses cannot overwrite a newer request. A failed overall request hides business values and offers recovery. Expired sessions offer a sign-in link.

The pagination defect was also repaired at the shared query layer: createdAt sorting now includes a unique id tie-breaker. Read-only checks against the configured database showed repeated IDs before the fix and complete, duplicate-free doctor and visit collections after the fix.

## Verification

The QA harness creates a fresh in-memory PostgreSQL-compatible database. Synthetic records are confined to that harness and test fixtures; the production dashboard has no fixture import or failure switch. Browser failure controls live only in audit/2026-10-06/workflows.mjs, on the localhost-bound QA server.
