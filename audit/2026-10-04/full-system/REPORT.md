**التاريخ: 4 أكتوبر 2026.** تمت مراجعة الفرونت والباك إند الموجودين في المشروع، وإصلاح المشاكل المؤكدة، ثم إعادة الاختبار. الوظائف التي اختُبرت أصبحت تعمل بالنتائج الموضحة أدناه. توجد قدرات ناقصة وقيود في تصميم البيانات مسجلة في آخر التقرير؛ لذلك هذه النتيجة ليست شهادة بأن كل سيناريو ممكن أو كل متطلب مستقبلي مكتمل.

## بيئة الاختبار وحدود البيانات

الفرونت والباك إند يعملان محليًا، لكن إعداد `DATABASE_URL` في الباك إند يشير إلى **قاعدة PostgreSQL خارجية**. لذلك تم إنشاء schema منفصلة باسم يبدأ بـ`goldera_qa_20261004_` داخل القاعدة نفسها. كل الكتابات والاختبارات استهدفت هذه المساحة فقط؛ لم تُعدّل سجلات التشغيل داخل `public`.

استُخدمت خمسة حسابات وهمية: مانيجر، سوبرفايزر، ميديكال ريب، مانيجر خارج الفريق، وميديكال ريب تابع للفريق الآخر. لم نستخدم حساب هند أو محمد عبد المعز الحقيقي؛ تم اختبار صلاحيات الأدوار المطلوبة بحسابات التجربة، مع إضافة دور السوبرفايزر للمراجعة.

المنافذ التجريبية كانت 5051 للباك إند، 3002 لواجهة التطوير، و3003 لمعاينة نسخة الإنتاج. ملفات PDF وCSV وExcel كانت اصطناعية. رفع PDF اختُبر على خدمة Cloudinary الفعلية، ثم نُظفت الملفات التجريبية. بيانات الاتصال لم تُكتب في التقرير أو ملفات النتائج.

**تحديث التنظيف النهائي:** تم تنفيذ خطوة التنظيف بنجاح عبر `node audit/2026-10-04/full-system/cleanup.mjs`؛ حُذفت الـschema التجريبية `goldera_qa_20261004_86266d2a4f` بالكامل دون أي تعديل على بيانات التشغيل في `public`، ونُظفت الملفات المؤقتة وأصول Cloudinary التجريبية، وتوثقت النتيجة رسميًا في [cleanup.json](/Users/marwan/Documents/Golderapharm/audit/2026-10-04/full-system/cleanup.json). كما تم تنظيف مسارات ومجلدات البناء المؤقتة (`.next-qa` و`.next-build` و`.next-final`) واستعادة الإشارة الطبيعية في `tsconfig.json` و`next-env.d.ts` مع استقرار بناء نسخة الإنتاج بنجاح.

هذا **اختبار مهام وفحص usability بواسطة الوكيل**. لم يُجرَ بحث مع مشاركين بشريين، أو قياس زمن إتمام المهام مع هند ومحمد، أو اختبار إمكانية وصول كامل بلوحة المفاتيح وقارئ شاشة. جرى التحقق من أسماء عناصر الاستخدام ورسائل الحقول والتأكيد والإلغاء والحالة المعلقة وظهور النتائج في المهام المذكورة.

## الحاجات الباقية، مرتبة للتطوير

هذه النقاط لم تُخفَ خلف رسائل نجاح وهمية. هي قيود فعلية أو قدرات ناقصة تحتاج دورة تنفيذ منفصلة أو قرارًا في قواعد العمل.

| P2 | المبيعات ترتبط باسم الصيدلية، وبعض JSON يرتبط باسم المنتج | حماية الحذف أُضيفت، لكن إعادة تسمية بيانات مستخدمة قد تجعل الربط بالأسماء غير متسق. نقل هذه العلاقات إلى IDs ثابتة مع ترحيل البيانات وتحديثات معاملية. |

## إعادة تشغيل الاختبار

الأدوات موجودة في هذا المجلد. لا تُشغَّل على بيانات التشغيل. `setup.mjs` ينشئ schema اختبار جديدة، و`runtime.mjs seed` يضيف الحسابات الوهمية. إعداد الاتصال المؤقت يُحفظ في `/private/tmp/goldera-full-qa.json` بصلاحيات 0600 ويُحذف بعد التنظيف. `schema.sql` لقطة مخطط قاعدة البيانات وقت هذه المراجعة ويجب تحديثه عند تغيير Prisma schema لاحقًا.

من جذر المشروع:

```sh
node audit/2026-10-04/full-system/setup.mjs
node audit/2026-10-04/full-system/runtime.mjs seed
node audit/2026-10-04/full-system/runtime.mjs
```

في terminal آخر للفرونت:

```sh
cd goldFront
NEXT_BUILD_DIR=.next-qa NEXT_PUBLIC_API_BASE_URL=http://localhost:5051 npm run dev -- --webpack --port 3002
```

ثم من الجذر، مع تغيير اسم التشغيل عند إعادة الاختبارات على نفس البيانات لتجنب عناوين/إيميلات الدفعات القديمة:

```sh
node audit/2026-10-04/full-system/api-tests.mjs new-run-name
node audit/2026-10-04/full-system/extended-tests.mjs
node audit/2026-10-04/full-system/route-tests.mjs
```

بعد إيقاف الخوادم التجريبية:

```sh
node audit/2026-10-04/full-system/cleanup.mjs
```

نتائج الفحص ولقطات الشاشة تبقى قابلة للمراجعة بعد حذف الحسابات والملفات التجريبية. التعديلات المصدرية موجودة في `goldFront` و`goldBack` في مساحة العمل.
